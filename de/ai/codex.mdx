[Codex](https://openai.com/index/introducing-codex/) ist OpenAIs Cloud-Coding-Agent. Er arbeitet direkt auf deinen GitHub-Repos. Du brauchst keine lokale Umgebung.

Codex und [Claude Code](/de/ai/claude-code) unterscheiden sich vor allem im Workflow. Codex läuft in der Cloud und arbeitet asynchron. Du beschreibst eine Aufgabe, lässt sie laufen und prüfst einen PR, wenn sie fertig ist. Das passt zu Batch-Aufgaben, etwa wenn du ein 500-zeiliges README in ein Dutzend Seiten aufteilst oder eine Troubleshooting-Seite aus deinen GitHub-Issues der letzten sechs Monate generierst. Weniger geeignet ist es für das Hin und Her beim Verfeinern einer einzelnen Seite. Für interaktive Arbeit an einer Seite nutze [Claude Code](/de/ai/claude-code).

## Schnelle Einrichtung

<Steps>
  <Step title="Repository öffnen">
    Öffne dein Jamdesk-Docs-GitHub-Repository in Codex.
  </Step>
  <Step title="Agent-Anweisungen hinzufügen">
    Erstelle im Projektstammverzeichnis eine Datei `AGENTS.md` mit deinen Dokumentationsstandards. Codex hält sich an die darin beschriebenen Konventionen.
  </Step>
  <Step title="MCP-Server verbinden">
    Füge deinen Docs-MCP-Endpunkt in `.codex/config.toml` hinzu. Codex kann dann in deiner veröffentlichten Dokumentation suchen.
  </Step>
</Steps>

## Vorlage für AGENTS.md

Erstelle `AGENTS.md` im Projektstammverzeichnis:

```markdown AGENTS.md
# Jamdesk Documentation Project

Jamdesk docs project. Pages are MDX (Markdown + React components). Config is in `docs.json`.

## How This Project Works

- `docs.json`: navigation structure, theme, colors, branding. Pages must be listed here to appear in the sidebar.
- `*.mdx` files: documentation pages. Every page needs `title` and `description` frontmatter.
- `images/`: static assets. Always use `.webp` format.
- `snippets/`: reusable MDX fragments. Import with `<Snippet file="name.mdx" />`.

## Page Template

Every page follows this structure:

    ---
    title: Clear, Specific Title
    description: One sentence. Used in search results and social previews.
    ---

    Opening paragraph: what this page covers and who it's for. No heading needed.

    ## First Section

    Content. Use components where they help, not for decoration.

    ## What's Next?

    <Columns cols={2}>
      <Card title="Related Page" icon="arrow-right" href="/path">
        Why the reader would go here next
      </Card>
    </Columns>

The opening paragraph comes right after frontmatter with no heading. "What's Next?" is always the last section. Card descriptions explain why, not what.

## Writing Style

Start with why. What problem does this solve? Show the answer first, then unpack the how.

Use progressive disclosure: simple example up top, advanced options tucked into Accordions or later sections.

Active voice. "Run this command", not "This command should be run".

One idea per paragraph. If you find yourself reaching for "also" or "additionally", that's the cue to start a new paragraph instead.

Code examples have to actually work. Every block should be complete and copy-pasteable, never partial or pseudocode.

And write like a person. No filler ("It's important to note that", "This allows you to"). No hedging ("you might want to consider"). If a paragraph reads like a chatbot wrote it, rewrite it shorter.

## Components

Only use these. Do not invent others.

Layout: Card, Columns, Tabs, Tab, Accordion, AccordionGroup, Steps, Step, Expandable, Frame, CodeGroup
Callouts: Note, Info, Warning, Tip, Check, Danger

| Use | For | Don't use for |
|-----|-----|---------------|
| Tabs | Mutually exclusive choices (npm/yarn, OS) | Sequential content |
| Steps | Ordered procedures | Unordered lists |
| Accordion | Optional/advanced detail | Core content |
| Card + Columns | Navigation links, feature grids | Inline content |
| Note/Tip/Warning | Important context | Every other paragraph |

Cards always go inside Columns:

    <Columns cols={2}>
      <Card title="Page Title" icon="icon-name" href="/path">
        Brief description
      </Card>
    </Columns>

Icons are Font Awesome Light names: "rocket", "code", "terminal", "book-open", "gear"

## Adding Pages

1. Create the `.mdx` file
2. Add the page path (no `.mdx` extension) to `docs.json` in the right navigation group
3. Link to it from related pages via "What's Next?" cards

If you skip step 2, the page won't show up in the sidebar. Read `docs.json` before creating pages so you understand the navigation structure.

## Common Mistakes

- Inventing components like `<CodeBlock>`, `<Alert>`, `<Section>`. They don't exist.
- Using `<Card>` without a `<Columns>` wrapper.
- Skipping `description` in frontmatter, which breaks search results and link previews.
- Using raw HTML tags instead of MDX components.
- Writing "click here" links instead of descriptive link text.
```

<Tip>
  Ergänze deine Produktterminologie, API-Namenskonventionen und alle Stilregeln, die speziell für deine Dokumentation gelten.
</Tip>

## MCP-Konfiguration

Füge deinen Docs-Endpunkt in `.codex/config.toml` hinzu:

```toml .codex/config.toml
[mcp_servers.my-docs]
url = "https://your-project.jamdesk.app/_mcp"
```

Ersetze `your-project` durch deine Jamdesk-Subdomain. Wenn eine eigene Domain live ist, verwende stattdessen diese: `url = "https://docs.acme.com/_mcp"`. Details zu den Endpunkten findest du unter [MCP-Server](/de/ai/mcp-server).

## Beispiel-Prompts

Codex führt Aufgaben asynchron aus. Gib ihm eine lange Aufgabe und schau später nach. Prompts, die ein größeres Arbeitspaket beschreiben, zahlen sich am meisten aus.

Ein guter erster Versuch: *„Schreibe Dokumentation für die Authentifizierungs-API auf Basis des Quellcodes in /src/auth“*. Codex liest deine Codebasis, findet die relevanten Dateien und erzeugt passende Seiten. Bei unübersichtlicheren Aufgaben nutze deine Bug-Historie. *„Erstelle eine Troubleshooting-Seite mit den 5 häufigsten Fehlern aus unseren GitHub-Issues“* liefert meist eine genauere Seite als alles, was du aus dem Gedächtnis schreiben würdest.

Umstrukturierungen über mehrere Dateien funktionieren in diesem Modus gut. Kopiere diesen Prompt in Codex für eine Aufgabe mit klaren Prüfkriterien:

<Prompt title="Großes README umstrukturieren">
Strukturiere das 500-zeilige `README.md` in fokussierte Jamdesk-Dokumentationsseiten um.

Akzeptanzkriterien:

- Erhalte jedes eindeutige technische Detail, jeden Befehl, jede Warnung und jedes Codebeispiel aus dem README.
- Gruppiere den Inhalt in aufgabenorientierte `.mdx`-Seiten mit aussagekräftigen Dateinamen.
- Gib jeder Seite `title`- und `description`-Frontmatter, einen Einleitungsabsatz und „Wie geht es weiter?“-Cards.
- Füge jede neue Seite der passenden Gruppe in `docs.json` hinzu und halte die Seitenreihenfolge logisch.
- Verwende nur Jamdesk-Komponenten, die bereits in `components/overview.mdx` aufgeführt sind; erfinde keine Komponenten.
- Korrigiere die internen Links für die neue Dateistruktur und melde jeden Quelllink, den du nicht auflösen kannst.
- Lösche das ursprüngliche README erst, wenn alle Inhalte abgedeckt sind und die neuen Seiten die Validierungs- und Broken-Link-Prüfungen des Projekts bestehen.
</Prompt>

## Der Skill „/update-jamdesk“

Installiere den Skill `/update-jamdesk`, um Dokumentation bei Code-Änderungen automatisch zu aktualisieren:

```bash
npx skills add jamdesk/skills --skill update-jamdesk -a codex
```

Die vollständige Anleitung findest du unter [Automatische Updates](/de/ai/automated-updates).
