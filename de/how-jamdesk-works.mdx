Jamdesk erstellt Dokumentationswebsites aus MDX-Dateien in deinem GitHub-Repository. Du schreibst Markdown mit React-Komponenten, pushst zu GitHub und deine Website ist in weniger als 60 Sekunden auf einem globalen CDN verfügbar. Deine Inhalte bleiben als einfache MDX-Dateien in deinem Repository, sodass du sie jederzeit zu einem anderen Tool verschieben kannst.

## Architekturüberblick

Dein Repository ist die maßgebliche Quelle. Jamdesk verbindet sich damit, erstellt deine Website und stellt sie in einem globalen Edge-Netzwerk bereit. Du musst keine Infrastruktur verwalten.

## Die Build-Pipeline

In der Regel dauert ein Build vom Anfang bis zum Ende 30–60 Sekunden. Builds sind schnell, weil Jamdesk Seiten nicht vorab rendert. Deine unverarbeiteten Inhalte gelangen zum Edge, und die Seiten werden bei Bedarf gerendert, wenn Besucher sie aufrufen.

<Steps>
  <Step title="Quelle abrufen">
    Du pushst zu deinem verbundenen GitHub-Branch (oder klickst im Dashboard auf Rebuild). Jamdesk klont dein Repository und sucht dein Dokumentationsverzeichnis.
  </Step>
  <Step title="Validierung">
    Deine `docs.json`-Konfiguration wird anhand des Schemas validiert. Außerdem werden interne Links auf fehlerhafte Seiten und ungültige Anker geprüft.
  </Step>
  <Step title="Inhalte verarbeiten">
    Jamdesk erstellt aus deinen Inhalten einen Suchindex, Embeddings für den [KI-Chat](/de/ai/chat), eine Sitemap, [`llms.txt`](/de/ai/llms-txt) und Weiterleitungsregeln.
  </Step>
  <Step title="Am Edge bereitstellen">
    Inhalte werden auf das CDN hochgeladen und an mehr als 300 Edge-Standorte verteilt. Es werden nur geänderte Dateien übertragen, sodass erneute Deployments schnell sind.
  </Step>
</Steps>

## Was einen Build auslöst

Ein Git-Push zu deinem verbundenen Branch, die Schaltfläche Rebuild im Dashboard oder [`jamdesk deploy`](/de/cli/deploy) über die CLI. Wenn du mehrere Commits kurz hintereinander pushst, fasst Jamdesk sie zu einem Build zusammen, damit keine unnötigen Ressourcen verbraucht werden.

Details zum Betrieb (Statusüberwachung, Rollbacks und Branch-Deployments) findest du unter [Build- und Bereitstellungszyklus](/de/deploy/lifecycle).

## Sicherheit und Infrastruktur

Darum musst du dich normalerweise nicht kümmern. Falls dein Sicherheitsteam nachfragt: Builds laufen in isolierten Containern, und die Verbindung über deine GitHub App ist schreibgeschützt.

<Columns cols={2}>
  <Card title="Minimale Berechtigungen" icon="shield-check">
    Die GitHub App fordert nur Lesezugriff auf die von dir ausgewählten Repositorys an. Die App hat keinen Schreibzugriff und fordert keine organisationsweiten Berechtigungen an.
  </Card>
  <Card title="Isolierte Builds" icon="box">
    Jeder Build erhält einen eigenen Container, der nach dem Deployment gelöscht wird. Zwischen Builds oder Kunden bleiben keine Daten erhalten.
  </Card>
  <Card title="HTTPS überall" icon="lock">
    Automatische SSL-Zertifikate für eigene Domains und Subdomains. Die Zertifikate werden automatisch ausgestellt und erneuert.
  </Card>
  <Card title="Globales CDN" icon="globe">
    Auslieferung über das Cloudflare-Netzwerk mit mehr als 300 Edge-Standorten und einer Verfügbarkeit von 99,9 %.
  </Card>
</Columns>

## Leistung

Ob deine Dokumentation gefunden wird, hängt zum Teil davon ab, wie schnell sie lädt. Google verwendet [Core Web Vitals](https://jamdesk.com/blog/why-google-pagespeed-matters) als Ranking-Signal. KI-Crawler wie GPTBot und ClaudeBot geben sich 1–5 Sekunden pro Seite. Lädt deine Dokumentation in diesem Zeitraum nicht, wird sie nicht zitiert.

Jede Jamdesk-Website wird vom Edge mit einer Zeit bis zum ersten Byte von unter 50 ms ausgeliefert. Das reicht aus, um Googles Ranking-Schwellenwerte einzuhalten und KI-Crawlern das Abrufen und Zitieren zu ermöglichen.

| Messwert | Typischer Wert |
|--------|---------------|
| Build-Dauer | 30-60 seconds |
| Verteilung des Deployments | < 30 seconds |
| Erstes Byte (Edge) | < 50ms |
| Vollständiger Seitenaufbau | < 500ms |
