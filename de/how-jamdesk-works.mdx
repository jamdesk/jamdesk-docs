Jamdesk erstellt Dokumentationsseiten aus MDX-Dateien in Ihrem GitHub-Repository. Schreiben Sie Markdown mit React-Komponenten und pushen Sie zu GitHub. Ihre Seite ist in unter 60 Sekunden über ein globales CDN live. Ihre Inhalte bleiben als einfache MDX-Dateien in Ihrem Repository. Sie können sie jederzeit in ein anderes Tool übertragen.

## Architekturüberblick

Ihr Repository ist die Quelle der Wahrheit. Jamdesk verbindet sich damit, erstellt Ihre Seite und deployt sie in ein globales Edge-Netzwerk.

## Die Build-Pipeline

Ein Build dauert typischerweise 30-60 Sekunden. Jamdesk rendert Seiten nicht im Voraus. Rohe Inhalte gehen an den Edge. Seiten werden bei Anfrage gerendert, wenn Besucher sie aufrufen.

<Steps>
  <Step title="Quellabruf">
    Sie pushen in Ihren verbundenen GitHub-Branch (oder klicken im Dashboard auf Rebuild). Jamdesk klont Ihr Repository und findet Ihr Dokumentationsverzeichnis.
  </Step>
  <Step title="Validierung">
    Jamdesk validiert `docs.json` gegen das Schema. Es prüft interne Links auf defekte Seiten und fehlerhafte Anker.
  </Step>
  <Step title="Inhaltsverarbeitung">
    Jamdesk erzeugt aus Ihren Inhalten Ihren Suchindex, die [KI-Chat](/de/ai/chat)-Embeddings, die Sitemap, [`llms.txt`](/de/ai/llms-txt) und Weiterleitungsregeln.
  </Step>
  <Step title="Deployment an den Edge">
    Inhalte werden auf das CDN hochgeladen und an über 300 Edge-Standorte verteilt. Nur geänderte Dateien werden übertragen.
  </Step>
</Steps>

## Was einen Build auslöst

Ein git push in Ihren verbundenen Branch, die Rebuild-Schaltfläche im Dashboard oder [`jamdesk deploy`](/de/cli/deploy) über die CLI. Jamdesk fasst kurz nacheinander gepushte Commits zu einem einzigen Build zusammen.

Operative Details (Statusüberwachung, Rollbacks, Branch-Deployments) finden Sie unter [Build- und Deploy-Lebenszyklus](/de/deploy/lifecycle).

## Sicherheit und Infrastruktur

Builds laufen in isolierten Containern. Builds lesen nur Ihr Repository.

<Columns cols={2}>
  <Card title="Minimale Berechtigungen" icon="shield-check">
    Die GitHub App fordert nur Zugriff auf von Ihnen ausgewählte Repositories an, keine organisationsweiten Scopes. Jamdesk schreibt nur dann in Ihr Repository, wenn Sie im Editor speichern, KI-Korrekturen über „Fix with AI“ übernehmen oder Übersetzungen aktivieren.
  </Card>
  <Card title="Isolierte Builds" icon="box">
    Jeder Build erhält einen eigenen Container, der nach dem Deployment zerstört wird. Zwischen Builds oder Kunden bleibt nichts erhalten.
  </Card>
  <Card title="Überall HTTPS" icon="lock">
    SSL-Zertifikate für jede Domain, automatisch ausgestellt und erneuert.
  </Card>
  <Card title="Globales CDN" icon="globe">
    Ausgeliefert über das Netzwerk von Cloudflare mit über 300 Edge-Standorten und 99,9 % Verfügbarkeit.
  </Card>
</Columns>

## Leistung

Die Ladegeschwindigkeit beeinflusst, ob Ihre Dokumentation gefunden wird. Google nutzt [Core Web Vitals](https://jamdesk.com/blog/why-google-pagespeed-matters) als Ranking-Signal. KI-Crawler wie GPTBot und ClaudeBot geben jeder Seite 1-5 Sekunden. Dokumentation, die in diesem Zeitfenster nicht lädt, wird nicht zitiert.

Jede Jamdesk-Seite wird vom Edge mit einer Time to First Byte von unter 50 ms ausgeliefert. Das ist schnell genug für Googles Ranking-Schwellenwerte und damit KI-Crawler Inhalte abrufen und zitieren können.

| Metrik | Typischer Wert |
|--------|---------------|
| Build-Zeit | 30-60 Sekunden |
| Deploy-Verteilung | < 30 Sekunden |
| First Byte (Edge) | < 50 ms |
| Vollständiges Laden der Seite | < 500 ms |
