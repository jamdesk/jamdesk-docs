Verwenden Sie die Builds-API, um Dokumentations-Neuaufbauten auszulösen, ohne neue Commits zu pushen. Das ist nützlich für CI-Pipelines, geplante Neuaufbauten oder Inhalte, die außerhalb Ihres Dokumentationsverzeichnisses generiert werden.

## Authentifizierung

Alle Anfragen verwenden einen Projekt-API-Schlüssel:

```http
Authorization: Bearer YOUR_API_KEY
```

Ihren API-Schlüssel finden Sie unter **Settings** → **API** für das Projekt.

## Einen Build auslösen

**POST** `https://api.jamdesk.com/projects/{project_id}/rebuild`

### Beispielanfrage

<CodeGroup>
```bash cURL
curl -X POST "https://api.jamdesk.com/projects/YOUR_PROJECT_ID/rebuild" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

```javascript JavaScript
const projectId = "YOUR_PROJECT_ID";
const apiKey = "YOUR_API_KEY";

const response = await fetch(
  `https://api.jamdesk.com/projects/${projectId}/rebuild`,
  {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${apiKey}`
    }
  }
);
const build = await response.json();
console.log(build.buildId, build.status);
```
</CodeGroup>

### Antwort

Erfolgreiche Anfragen geben `200 OK` mit Build-Metadaten zurück, mit denen Sie den Fortschritt verfolgen können.

```json
{
  "buildId": "build_8f3k2j",
  "status": "queued",
  "createdAt": "2026-02-05T10:30:00Z",
  "commit": {
    "sha": "a1b2c3d",
    "message": "Update API docs",
    "author": "jane@example.com"
  },
  "project": {
    "id": "proj_abc123",
    "name": "My Docs"
  }
}
```

<Note>
Wenn Sie eine `429`-Antwort erhalten, versuchen Sie es mit exponentiellem Backoff erneut. Kontaktieren Sie den Support, wenn Sie höhere Limits benötigen.
</Note>

### Antwortfelder

<ResponseField name="buildId" type="string">
  Eindeutige Build-ID. Verwenden Sie diese, um den Build im Dashboard zu referenzieren.
</ResponseField>

<ResponseField name="status" type="string">
  Aktueller Build-Status. Einer von: `queued`, `building`, `deployed`, `failed`.
</ResponseField>

<ResponseField name="createdAt" type="string">
  ISO-8601-Zeitstempel der Build-Erstellung.
</ResponseField>

<ResponseField name="commit.sha" type="string">
  Kurzer Commit-Hash, der den Build ausgelöst hat.
</ResponseField>

<ResponseField name="commit.message" type="string">
  Commit-Nachricht aus dem Quell-Repository.
</ResponseField>

<ResponseField name="commit.author" type="string">
  E-Mail-Adresse des Commit-Autors.
</ResponseField>

<ResponseField name="project.id" type="string">
  Projektkennung, die Ihrem Dashboard-Projekt entspricht.
</ResponseField>

<ResponseField name="project.name" type="string">
  Anzeigename des Projekts.
</ResponseField>

## Build-Status verfolgen

Der Build-Status ist im Dashboard unter **Deployments** sichtbar. Jeder Build durchläuft diese Phasen:

1. **queued**: Der Build wartet in der Warteschlange.
2. **building**: Der Build-Dienst kompiliert Ihre Dokumentation.
3. **deployed**: Der Build ist abgeschlossen und Ihre Website ist live.
4. **failed**: Etwas ist schiefgelaufen. Prüfen Sie die Build-Logs für Details.

Wenn Ihr Repository mit GitHub verbunden ist, aktualisieren sich die Commit-Statusprüfungen automatisch. Ein grünes Häkchen erscheint am Commit, wenn der Build bereitgestellt wird. Ein rotes X erscheint, wenn der Build fehlschlägt. Sie müssen die API nicht abfragen, um Status-Updates zu erhalten.

## Format von Fehlerantworten

Fehlerantworten folgen einer einheitlichen Struktur:

```json
{
  "error": {
    "code": "unauthorized",
    "message": "Invalid API key",
    "status": 401
  }
}
```

<ResponseField name="error.code" type="string">
  Maschinenlesbarer Fehlercode. Mögliche Werte finden Sie in der folgenden Tabelle.
</ResponseField>

<ResponseField name="error.message" type="string">
  Menschenlesbare Beschreibung des Fehlers.
</ResponseField>

<ResponseField name="error.status" type="number">
  HTTP-Statuscode der Antwort.
</ResponseField>

### Fehlercodes

| Status | Code | Message | Fix |
|--------|------|---------|-----|
| **401** | `unauthorized` | Invalid API key | Schlüssel unter **Settings** → **API** neu generieren |
| **403** | `forbidden` | Unauthorized project access | Prüfen, ob die Projekt-ID zum Projekt des API-Schlüssels passt |
| **404** | `project_not_found` | Project not found | Projekt-ID im Dashboard überprüfen |
| **429** | `rate_limited` | Too many requests | Zurückhalten und mit exponentiellem Backoff erneut versuchen |
| **500** | `internal_error` | Internal server error | Nach einigen Sekunden erneut versuchen. Support kontaktieren, falls das Problem bestehen bleibt |
