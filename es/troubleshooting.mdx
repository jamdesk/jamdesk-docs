## Fallos de build

Tu dashboard muestra un build como "Failed". La mayoría de los fallos provienen de una de tres causas: una página MDX con una importación o componente roto, una edición no válida de `docs.json` (corchetes sin cerrar, comas finales después del último elemento de un array) o una página listada en la navegación de `docs.json` que no existe como archivo `.mdx`. Las dos primeras salen a la luz localmente con `jamdesk dev` antes de llegar a un build desplegado. Ejecutarlo una vez antes de hacer push suele ahorrar una vuelta innecesaria.

<Tip>
El log de build en tu dashboard muestra el archivo y la línea exactos donde ocurrió el error. Empieza por ahí. Casi siempre señala el problema real, no solo el síntoma.
</Tip>

Para códigos de error específicos, consulta [Fallos de build](/es/help/troubleshooting/build-failures) y la [Referencia de errores](/es/help/troubleshooting/error-reference).

## El dominio personalizado no se verifica

¿El dominio se queda en "Pending" después de añadir los registros DNS? Repasa esto en orden:

1. Confirma que añadiste el registro **TXT** `_jamdesk.<hostname>`. El enrutamiento no se activa sin él, y la ausencia del TXT es la causa más común de un dominio en Pending. El hostname es el dominio completo que estás verificando (para `docs.example.com`, el nombre del registro TXT es `_jamdesk.docs.example.com`).
2. Confirma que añadiste un registro **CNAME** (no un registro A) para subdominios.
3. Si usas Cloudflare, configura el proxy como **DNS only** (nube gris) para ambos registros.
4. Comprueba la propagación en [whatsmydns.net](https://www.whatsmydns.net/).

```bash
# Verify the TXT verification record
dig TXT _jamdesk.docs.yourdomain.com

# Verify your CNAME is resolving
dig CNAME docs.yourdomain.com
```

Algo no obvio que vale la pena saber: incluso después de que `dig` muestre que tus registros se resuelven, el dashboard puede seguir mostrando "Pending" hasta 30 minutos. El verificador está detrás de resolvedores upstream que almacenan en caché las respuestas DNS negativas, y esa ventana de caché tiene que expirar antes de que la revalidación tenga éxito. Si todo se resuelve localmente pero el dashboard no se ha actualizado, dale media hora antes de asumir un problema más profundo.

[Solución de problemas de DNS](/es/help/troubleshooting/dns-issues) cubre particularidades específicas de cada proveedor.

## El repositorio de GitHub no aparece

Si tu repositorio no está en la lista al crear un proyecto, probablemente la GitHub App de Jamdesk no está instalada en la organización del repositorio, o el acceso a repositorios está configurado como "Selected repositories" sin incluir el tuyo. Vuelve a autorizar en [github.com/settings/installations](https://github.com/settings/installations) y concede acceso a "All repositories" o al repositorio específico que necesitas.

Consulta [Problemas de GitHub](/es/help/troubleshooting/github-issues) para problemas de webhooks y permisos.

## Faltan datos de analítica

Hay algunas razones comunes por las que tu dashboard muestra cero visitantes. La analítica tarda hasta 24 horas en aparecer tras el primer deploy de un sitio, así que los proyectos recién creados se ven vacíos durante un tiempo. Los bloqueadores de anuncios y Do Not Track impiden contar una parte de las visitas, así que tus cifras siempre irán por detrás de tus logs de servidor. Si ninguno de estos casos aplica, confirma que tu sitio esté realmente desplegado y accesible públicamente.

[Problemas de analítica](/es/help/troubleshooting/analytics-issues) profundiza en datos retrasados o faltantes.

## Problemas de inicio de sesión

¿No puedes iniciar sesión, o te devuelve a la pantalla de login? Borra la caché y las cookies de `dashboard.jamdesk.com`, luego prueba en una ventana de incógnito. Si inicias sesión con GitHub, tu email de GitHub debe coincidir con el email de tu cuenta de Jamdesk.

Consulta [Problemas de inicio de sesión](/es/help/troubleshooting/login-issues) para conocer los pasos de recuperación de cuenta.
