Jamdesk can repair many of the broken links and missing page descriptions a build reports. The **Fix with AI** button reads those build warnings and proposes an edit for each one. It commits the fixes you approve to your connected GitHub repository. The commit starts a new build.

The [`jamdesk fix` CLI command](/cli/fix-broken-links) does the same in your terminal. It writes to your working copy and leaves the commit to you.

## What it fixes

Fix with AI repairs three kinds of build warning:

- **Broken internal links:** a link fragment that points at a heading which no longer exists on the target page, such as a typo (`#instalation` → `#installation`), or a translated page whose heading was renamed.
- **Missing page descriptions:** a page with no `description` in its frontmatter. Jamdesk writes a short summary from the page content for you to review.
- **Missing page titles:** a page with no title gets a suggested one from the page content, for you to review.

It proposes a change only when it can resolve the target with confidence. It lists anything ambiguous separately for you to fix by hand.

Fix with AI makes up to 1,000 AI requests per project in a 24-hour period. Results for pages that haven't changed are reused and don't count toward the limit.

<Note>
  The fixable count is not the same as the warning count. A build can show five warnings while Fix with AI offers to repair three of them. The other two have no unambiguous fix.
</Note>

## Prerequisites

- A [connected GitHub repository](/integrations/github) for the project.
- Write access for the Jamdesk GitHub App to commit the fixes. The modal shows a **Grant access** link to GitHub when access is missing.
- A completed build that carries broken-link or missing-description warnings.

## Find the banner

Open your project and scroll to **Build History** on the Project Home page. A banner with a count and a **Fix with AI** button appears above the build list when your latest build has fixable issues.

The banner appears only on your newest completed build. Fixes always apply to the current state of your docs.

## Review and apply the fixes

<Steps>
  <Step title="Open the preview">
    Click **Fix with AI**. The modal opens. The AI agent takes a few seconds to review your docs and build a fix plan.
  </Step>
  <Step title="Read each proposed change">
    Fixes are grouped by type. **Broken links** shows each rewritten anchor. **Missing descriptions** shows the suggested summary for each page. **Missing titles** shows the proposed title. Clear the checkbox on anything to skip it this time. Use the ignore button to [silence a recommendation for good](#ignore-recommendations). Issues with no clear fix appear under **Can't be fixed automatically** for you to fix by hand.

    <Frame>
      <img src="/images/fix-with-ai/modal.webp" alt="The Fix with AI modal. A Broken links section lists three checked fixes, each showing the old anchor struck through and the corrected anchor. A Can't be fixed automatically section lists two issues to fix by hand, above Cancel and Apply 3 fixes buttons." />
    </Frame>
  </Step>
  <Step title="Apply">
    Click **Apply fixes**. Jamdesk commits the selected changes to your connected branch with the message `docs: apply AI-suggested fixes (via Jamdesk)` and starts a new build.
  </Step>
  <Step title="Confirm the rebuild">
    Watch the new build in [Build History](/builds/monitoring). The fixed warnings are gone once it goes live. Anything left is either a warning Fix with AI could not resolve or a new issue from the latest content.
  </Step>
</Steps>

<Note>
  Applying writes a real commit to your repository. Review or revert it on GitHub like any other commit.
</Note>

## When some issues can't be fixed

The modal lists warnings with no clear fix under a separate heading and leaves them alone. Common reasons:

- A broken link whose target page or heading doesn't exist anywhere.
- A navigation entry with no matching source file.
- A page where the agent could not generate a description.

These need a manual edit. Open the page in the [editor](/development/local-preview) or your code editor. Correct the link or add the description. Push to rebuild.

## Ignore recommendations

Some warnings aren't worth acting on: a link you broke on purpose, or a stub page that needs no description. Unchecking a fix only skips it once. Ignoring removes it from the count until you restore it.

Every row in the modal has an ignore button, fixable or not. Clicking it moves the item to a collapsed **Ignored** section at the bottom. The banner count on the Project Home page drops to match after you close the modal. The matching warnings disappear from Build History on the current build and every build after it. **Ignore all** does the same for everything still listed.

How ignores behave:

- **Shared and persistent:** ignores apply to the whole project. Every member sees the same list. It carries across builds. Jamdesk matches each warning by its content, not its line number. Editing other parts of the page won't bring an ignored item back.
- **Restoring:** expand the **Ignored** section and click **Restore** on any item. Ignoring everything on a build hides the banner. A small "N ignored recommendations" link under Build History then reopens the modal.
- **Changed warnings come back:** an ignored item returns as a new recommendation when the underlying issue changes, for example when the broken link now points somewhere else.

## Fix with AI vs. the CLI

The dashboard and the CLI fix broken-link anchors. They differ in where they run and how the change lands.

| | Fix with AI (dashboard) | [`jamdesk fix`](/cli/fix-broken-links) (CLI) |
|---|---|---|
| Runs | In the dashboard, on a build | In your terminal, against local files |
| Fixes | Broken links and missing descriptions | Broken-link anchors |
| Commit | Commits to your branch for you | Writes local files; you commit |
| Trigger | One click on the build banner | `jamdesk fix` |

Use the dashboard flow for a quick repair without leaving Jamdesk. Use the CLI when you want the changes in your working copy first, for example to bundle them with other edits.
