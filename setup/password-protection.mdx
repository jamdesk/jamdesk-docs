---
title: Password Protection
description: Lock your entire docs site or specific pages behind a password. Visitors see an unlock screen before accessing protected content.
---

Password protection lets you restrict access to your documentation. You can lock the entire site or just specific pages — useful for internal runbooks, pre-release docs, or gated content.

## Enabling password protection

In the dashboard, go to **Settings** and toggle **Password Protection** on. Set a password that you'll share with authorized readers.

When protection is active, visitors see an unlock screen before they can view any content.

## Configuration options

You can fine-tune protection in your `docs.json`:

```json docs.json
{
  "auth": {
    "password": {
      "enabled": true,
      "hint": "Ask your team lead for the password"
    }
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `enabled` | `boolean` | Lock the entire site. Overrides per-page settings |
| `hint` | `string` | Optional hint shown on the unlock screen |

## Protecting specific pages

If you only want to lock specific pages — not the whole site — mark them private. The next build will auto-activate password protection in *specific pages* mode, and the dashboard will prompt you to set a password.

Two ways to mark a page private:

**In the page's frontmatter:**

```yaml
---
title: Internal runbook
private: true
---
```

**In `docs.json`:**

```json docs.json
{
  "auth": {
    "password": {
      "private": ["/internal/runbook", "/admin/settings"]
    }
  }
}
```

With either approach, every *other* page stays public.

### Precedence

- If a page is marked both `public: true` and `private: true`, **public wins** (safer default).
- If `auth.password.enabled: true` is set anywhere in `docs.json`, it locks the whole site and `private` markers become redundant.
- If the password isn't set yet, private pages remain accessible until you set one in the dashboard — the dashboard shows a prominent warning in that state.

### Removing protection

Removing all `private: true` markers and pushing to your repo will turn off password protection on the next build. **This also deletes the stored password** — you'll need to set a new one if you re-enable protection later.
