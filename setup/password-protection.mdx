---
title: Password Protection
description: Lock your entire docs site or just a handful of pages behind a shared password. Visitors get an unlock screen; the rest of your docs stay open.
---

Sometimes you want your documentation online, discoverable, versioned in Git, but not visible to the world. Runbooks, pre-release guides, partner-only docs, early-access features. Password protection gives you a single shared passphrase that gates either your whole site or a specific set of pages, without moving anything out of your existing repo.

Jamdesk supports two modes, and you pick between them in your `docs.json`:

- **Whole site** locks everything behind the password.
- **Specific pages** keeps most pages public and only gates pages you mark private.

Both modes share the same unlock screen, the same dashboard controls, and the same rotation flow. The only difference is how much of the site is gated.

## Whole-site mode

Use this when everything is private: internal engineering docs, a staging copy of your public site, a product you haven't launched yet.

Add this to your `docs.json` and push to your repo:

```json docs.json
{
  "auth": {
    "password": {
      "enabled": true,
      "hint": "Ask your account manager for the password"
    }
  }
}
```

The next build turns protection on. You'll see the dashboard card flip from **Off** to **Password not set**, and the Settings page will show a prominent notice asking you to pick a password. Until you do, the site stays closed and returns `401` for every page.

![Dashboard Password Protection card while protection is off, showing the docs.json snippet to copy](/images/password-protection/dashboard-pp-off.webp)

Once you set a password on the Settings page, the card moves to the **On** state:

![Dashboard Password Protection card in the On state, showing the rotate password form and revoke sessions button](/images/password-protection/dashboard-pp-on.webp)

From here you can rotate the password, revoke all active sessions, and see when it was last changed. Rotation takes effect immediately on the next request and doesn't require a rebuild.

### Public exceptions

Whole-site mode has one escape hatch: you can keep specific pages public even while the rest of the site is gated. This is how you publish a marketing landing page or a signup form alongside private docs.

You've got three ways to mark a page public, and they all merge into the same allow-list on each build.

Frontmatter is the most granular option. Add `public: true` to any `.mdx` file and only that page escapes the gate. Navigation groups cover a whole section at once: set `public: true` on a `group` or `tab` in `docs.json`, and every page under it is public. For paths that don't map neatly to either (say, a dynamically-generated route or a top-level page you'd rather keep out of nav), `auth.password.public[]` takes a plain array of paths and globs.

```json docs.json
{
  "auth": {
    "password": {
      "enabled": true,
      "hint": "Ask your account manager",
      "public": ["/marketing/**", "/changelog"]
    }
  }
}
```

Globs support `*` (matches one path segment) and `**` (matches any depth). A bare `/` is rejected. If it were allowed, a single typo could silently disable the password wall for your entire site, which is not a failure mode anyone wants.

## Specific-pages mode

Use this when most of your docs are public and you just need to hide a small number of pages: a single admin runbook, a few beta features, an internal reference that sits inside an otherwise-public section.

In this mode you don't set `auth.password.enabled` at all. Instead, you mark individual pages private. The next build detects the private pages, activates protection in specific-pages mode, and the dashboard prompts you to set a password, exactly like whole-site mode.

Two equivalent ways to mark a page private:

**In the page's frontmatter:**

```yaml
---
title: Incident Runbook
private: true
---
```

**In `docs.json`:**

```json docs.json
{
  "auth": {
    "password": {
      "hint": "Ask the on-call engineer",
      "private": ["/admin/runbook", "/internal/api-keys"]
    }
  }
}
```

Pick whichever feels more natural. Frontmatter is easier when you're deciding page-by-page; the `docs.json` list is easier when someone wants a single place to audit what's gated.

The dashboard card shows the resolved list of private pages after each build, so you can sanity-check that the build picked up what you expected:

![Dashboard Password Protection card in specific-pages mode, listing three private paths](/images/password-protection/dashboard-pp-specific.webp)

## What visitors see

When someone hits a gated page, they get a centered unlock card with no sidebar, no chrome, and no indication of what's behind the door besides the site name and an optional hint.

![ACME unlock screen with site name, lock icon, password field, and hint text below](/images/password-protection/unlock-screen.webp)

The form is branded with your site's logo and primary color from `docs.json`. The `hint` field is optional but recommended; it's the only on-screen clue about how to get the password, so write something like "Ask #docs-access on Slack" rather than leaving people stranded.

Wrong passwords render the same card with an error message, a fresh input, and a small delay between attempts. An incorrect password and a request without a password both land on the same screen, so nothing on the page distinguishes "password wrong" from "no password entered yet."

![Unlock screen after a failed attempt, with 'Incorrect password. Please try again.' in red](/images/password-protection/unlock-screen-error.webp)

Once a visitor enters the correct password, they get a signed cookie and can browse normally until the session expires or you revoke it.

## Rotating the password

Passwords get shared. People leave. You'll want to change it eventually. Open the Password Protection card, type a new passphrase in the **Rotate password** field, click **Save new password**. That's it. Everyone with the old password is immediately locked out on their next request; everyone with the new password gets in.

If you've just had someone leave the team and want to force-logout every existing session without changing the passphrase, click **Revoke all sessions** instead. It bumps a server-side version counter, which invalidates every cookie that was issued before the bump. Visitors will need to re-enter the password; you don't need to tell anyone the new password because there isn't one.

## Disabling protection

Protection is driven by `docs.json`, so disabling it means editing the file and pushing.

- **Whole site:** remove `auth.password.enabled` (or set it to `false`).
- **Specific pages:** remove every `private: true` marker and clear `auth.password.private`.

On the next build, Jamdesk deletes the stored password hash and flips the card back to **Off**. No "dormant" state lingers. If you re-enable protection later, you'll need to pick a fresh password.

<Warning>
  Your source repo isn't password-protected. Password protection gates the
  hosted docs site at `*.jamdesk.app` (or your custom domain). If your GitHub
  repo is public, the MDX content is still readable there. Make the repo
  private if you need full content protection.
</Warning>

## Precedence rules

A single page can be touched by several signals at once. The resolution order, from most to least specific:

- If `auth.password.enabled` is `true`, the whole site is gated. `private: true` on individual pages becomes redundant.
- If a page is marked both `public: true` and `private: true`, **public wins**. The safer default is the one that doesn't accidentally leak a page.
- Frontmatter `public: true`, nav-group `public: true`, and `auth.password.public[]` globs all merge together into one allow-list. No "most specific wins" rule. If any signal says a page is public, it's public.
- If `auth.password.private[]` is set but `auth.password.enabled` is not, Jamdesk activates specific-pages mode automatically. You don't need to do anything else.

## Configuration reference

For the exact schema and field descriptions, see [`docs.json` reference](/config/docs-json-reference#auth-password). The short version:

| Field | Type | Purpose |
|-------|------|---------|
| `auth.password.enabled` | `boolean` | Whole-site mode opt-in. Requires a password to be set in the dashboard before the gate activates. |
| `auth.password.hint` | `string` (max 200 chars) | Plain-text hint shown on the unlock screen. |
| `auth.password.public` | `string[]` | Paths or globs that bypass the password. Merged with frontmatter `public: true`. |
| `auth.password.private` | `string[]` | Exact paths that require the password. Setting this without `enabled` activates specific-pages mode. |
