Jamdesk crea siti di documentazione dai file MDX nel tuo repository GitHub. Scrivi Markdown con componenti React, esegui il push su GitHub e il tuo sito sarà online su un CDN globale in meno di 60 secondi. I contenuti restano nel repository come semplici file MDX, quindi puoi trasferirli a un altro strumento in qualsiasi momento.

## Panoramica dell'architettura

Il tuo repository è la fonte autorevole. Jamdesk si connette al repository, crea il sito e lo distribuisce su una rete edge globale. Non devi gestire alcuna infrastruttura.

## La pipeline di build

In genere richiede 30-60 secondi dall'inizio alla fine. I build sono rapidi perché Jamdesk non esegue il pre-rendering delle pagine. I contenuti grezzi vengono inviati all'edge e le pagine vengono renderizzate su richiesta quando i visitatori le richiedono.

<Steps>
  <Step title="Recupero della sorgente">
    Esegui il push sul branch GitHub connesso (oppure seleziona Rebuild nel dashboard). Jamdesk clona il repository e individua la directory della documentazione.
  </Step>
  <Step title="Convalida">
    La configurazione `docs.json` viene convalidata rispetto allo schema e i link interni vengono controllati per individuare pagine inesistenti e anchor non validi.
  </Step>
  <Step title="Elaborazione dei contenuti">
    Jamdesk genera l'indice di ricerca, gli embedding per la [chat AI](/it/ai/chat), la sitemap, [`llms.txt`](/it/ai/llms-txt) e le regole di reindirizzamento dai tuoi contenuti.
  </Step>
  <Step title="Deploy sull'edge">
    I contenuti vengono caricati sul CDN e propagati in oltre 300 località edge. Vengono trasferiti solo i file modificati, quindi i nuovi deploy sono rapidi.
  </Step>
</Steps>

## Cosa attiva un build

Un push Git sul branch connesso, il pulsante Rebuild nel dashboard oppure [`jamdesk deploy`](/it/cli/deploy) dalla CLI. Se esegui il push di più commit in rapida successione, Jamdesk li raggruppa in un unico build per evitare di consumare risorse inutilmente.

Per i dettagli operativi (monitoraggio dello stato, rollback, variabili d'ambiente e deploy dei branch), consulta [Ciclo di build e deploy](/it/deploy/lifecycle).

## Sicurezza e infrastruttura

Non devi occuparti di questi aspetti, ma se il tuo team di sicurezza lo chiede: i build vengono eseguiti in container isolati e la connessione alla tua GitHub App è di sola lettura.

<Columns cols={2}>
  <Card title="Permessi minimi" icon="shield-check">

  </Card>
  <Card title="Build isolati" icon="box">

## Prestazioni

La possibilità che la tua documentazione venga trovata dipende anche dalla velocità di caricamento. Google utilizza i [Core Web Vitals](https://jamdesk.com/blog/why-google-pagespeed-matters) come segnale di ranking e i crawler AI come GPTBot e ClaudeBot si concedono da 1 a 5 secondi per pagina. Se la documentazione non si carica entro questo intervallo, non verrà citata.

Ogni sito Jamdesk viene distribuito dall'edge con un tempo al primo byte inferiore a 50 ms. È sufficientemente veloce per le soglie di ranking di Google e consente ai crawler AI di recuperare e citare i contenuti.

| Metrica | Valore tipico |
|--------|---------------|
| Durata del build | 30-60 secondi |
| Propagazione del deploy | < 30 secondi |
| Primo byte (edge) | < 50 ms |
| Caricamento completo della pagina | < 500 ms |
