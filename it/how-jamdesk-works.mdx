Jamdesk crea siti di documentazione a partire dai file MDX nel tuo repository GitHub. Scrivi in Markdown con componenti React, esegui il push su GitHub e il tuo sito è online su una CDN globale in meno di 60 secondi. I contenuti restano nel tuo repository come semplici file MDX, così puoi trasferirli a un altro strumento in qualsiasi momento.

## Panoramica dell'architettura

Il tuo repository è la fonte di verità. Jamdesk si collega al repository, crea il tuo sito e lo distribuisce su una rete edge globale. Non devi gestire alcuna infrastruttura.

## La pipeline di build

In genere, il processo completo richiede 30-60 secondi. Le build sono rapide perché Jamdesk non esegue il pre-rendering delle pagine. I contenuti originali vengono inviati all'edge e le pagine vengono renderizzate su richiesta, quando i visitatori le richiedono.

<Steps>
  <Step title="Recupero del codice sorgente">
    Esegui il push sul branch GitHub collegato (oppure fai clic su Rebuild nella dashboard). Jamdesk clona il tuo repository e individua la directory della documentazione.
  </Step>
  <Step title="Convalida">
    La configurazione `docs.json` viene convalidata rispetto allo schema e i link interni vengono controllati per individuare pagine mancanti e ancore non valide.
  </Step>
  <Step title="Elaborazione dei contenuti">
    Jamdesk genera l'indice di ricerca, gli embedding per la [chat AI](/it/ai/chat), la sitemap, [`llms.txt`](/it/ai/llms-txt) e le regole di reindirizzamento a partire dai tuoi contenuti.
  </Step>
  <Step title="Distribuzione sull'edge">
    I contenuti vengono caricati sulla CDN e propagati a oltre 300 località edge. Vengono trasferiti solo i file modificati, perciò le nuove distribuzioni sono rapide.
  </Step>
</Steps>

## Cosa attiva un build

Un push Git sul branch collegato, il pulsante Rebuild nella dashboard oppure [`jamdesk deploy`](/it/cli/deploy) dalla CLI. Se esegui il push di più commit in rapida successione, Jamdesk li raggruppa in un'unica build per evitare di sprecare risorse.

Per i dettagli operativi (monitoraggio dello stato, rollback e distribuzioni dei branch), consulta [Ciclo di build e distribuzione](/it/deploy/lifecycle).

## Sicurezza e infrastruttura

Non devi preoccuparti di questi aspetti, ma se il tuo team addetto alla sicurezza te lo chiede: le build vengono eseguite in container isolati e la connessione alla GitHub App è di sola lettura.

<Columns cols={2}>
  <Card title="Permessi minimi" icon="shield-check">
    La GitHub App richiede solo l'accesso in lettura ai repository che selezioni. L'app non dispone dell'accesso in scrittura e non richiede autorizzazioni a livello di organizzazione.
  </Card>
  <Card title="Build isolate" icon="box">
    Ogni build viene eseguita nel proprio container, che viene eliminato dopo la distribuzione. Nulla viene conservato tra una build e l'altra o tra clienti diversi.
  </Card>
  <Card title="HTTPS ovunque" icon="lock">
    Certificati SSL automatici per domini personalizzati e sottodomini. I certificati vengono emessi e rinnovati automaticamente.
  </Card>
  <Card title="CDN globale" icon="globe">
    I contenuti vengono distribuiti dalla rete Cloudflare, con oltre 300 località edge e un tempo di attività del 99,9%.
  </Card>
</Columns>

## Prestazioni

La possibilità che la tua documentazione venga trovata dipende anche dalla velocità di caricamento. Google usa [Core Web Vitals](https://jamdesk.com/blog/why-google-pagespeed-matters) come fattore di ranking e i crawler AI, come GPTBot e ClaudeBot, si concedono da 1 a 5 secondi per pagina. Se la tua documentazione non si carica in quel tempo, non viene citata.

Ogni sito Jamdesk viene distribuito dall'edge e offre un time to first byte inferiore a 50 ms. È abbastanza veloce da rispettare le soglie di ranking di Google e consentire ai crawler AI di recuperare e citare i contenuti.

| Metrica | Valore tipico |
|--------|---------------|
| Tempo di build | 30-60 secondi |
| Propagazione della distribuzione | < 30 secondi |
| Primo byte (edge) | < 50ms |
| Caricamento completo della pagina | < 500ms |
