Jamdesk construit des sites de documentation à partir de fichiers MDX dans votre dépôt GitHub. Vous rédigez du Markdown avec des composants React, poussez vers GitHub, et votre site est en ligne sur un CDN mondial en moins de 60 secondes. Votre contenu reste dans votre dépôt sous forme de fichiers simples. Rien de propriétaire, rien à migrer.

## Vue d'ensemble de l'architecture

Votre dépôt est la source de vérité. Jamdesk s'y connecte, build votre site et le déploie sur un réseau de périphérie mondial. Vous ne gérez aucune infrastructure.

## Le pipeline de build

Généralement entre 30 et 60 secondes, du début à la fin. Les builds sont rapides car Jamdesk ne pré-rend pas les pages. Votre contenu brut est envoyé vers la périphérie, et les pages s'affichent à la demande lorsque les visiteurs les demandent.

<Steps>
  <Step title="Récupération de la source">
    Vous poussez vers votre branche GitHub connectée (ou cliquez sur Rebuild dans le dashboard). Jamdesk clone votre dépôt et localise votre répertoire de documentation.
  </Step>
  <Step title="Validation">
    Votre configuration `docs.json` est validée par rapport au schéma, et les liens internes sont vérifiés pour détecter les pages manquantes et les ancres incorrectes.
  </Step>
  <Step title="Traitement du contenu">
    Jamdesk génère votre index de recherche, les embeddings pour le [chat IA](/fr/ai/chat), le sitemap, [`llms.txt`](/fr/ai/llms-txt) et les règles de redirection à partir de votre contenu.
  </Step>
  <Step title="Déployer vers la périphérie">
    Le contenu est téléchargé sur le CDN et propagé vers 300+ emplacements en périphérie. Seuls les fichiers modifiés sont transférés, ce qui rend les redéploiements rapides.
  </Step>
</Steps>

## Ce qui déclenche un build

Un git push vers votre branche connectée, le bouton Rebuild dans le dashboard, ou [`jamdesk deploy`](/fr/cli/deploy) depuis la CLI. Si vous poussez plusieurs commits en succession rapide, Jamdesk les regroupe en un seul build pour ne pas gaspiller de ressources.

Pour les détails opérationnels (surveillance de l'état, rollbacks, variables d'environnement, déploiements par branche), consultez [Cycle de vie Build & Deploy](/fr/deploy/lifecycle).

## Sécurité et infrastructure

Vous n'avez pas besoin de vous préoccuper de ces éléments, mais si votre équipe de sécurité pose des questions : les builds s'exécutent dans des conteneurs isolés et votre connexion GitHub App est en lecture seule.

## Performance

La visibilité de votre documentation dépend en partie de sa vitesse de chargement. Google utilise les [Core Web Vitals](https://www.jamdesk.com/blog/why-google-pagespeed-matters) comme signal de classement, et les robots d'exploration IA tels que GPTBot et ClaudeBot s'accordent entre 1 et 5 secondes par page. Si votre documentation ne se charge pas dans cette fenêtre, elle ne sera pas citée.

Chaque site Jamdesk est servi depuis la périphérie avec un temps jusqu'au premier octet inférieur à 50 ms. Assez rapide pour Google, assez rapide pour être cité par les robots d'exploration IA.

| Métrique | Valeur typique |
|--------|---------------|
| Durée du build | 30-60 secondes |
| Propagation du déploiement | < 30 secondes |
| Premier octet (périphérie) | < 50 ms |
| Chargement complet de la page | < 500 ms |
