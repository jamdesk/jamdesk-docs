Jamdesk build des sites de documentation à partir de fichiers MDX dans votre dépôt GitHub. Vous écrivez du Markdown avec des composants React, vous poussez sur GitHub, et votre site est en ligne sur un CDN mondial en moins de 60 secondes. Votre contenu reste dans votre dépôt sous forme de fichiers MDX classiques, vous pouvez donc le migrer vers un autre outil à tout moment.

## Vue d'ensemble de l'architecture

Votre dépôt est la source de vérité. Jamdesk s'y connecte pour build votre site et le déployer sur un réseau edge mondial. Vous n'avez aucune infrastructure à gérer.

## Le pipeline de build

Généralement entre 30 et 60 secondes, du début à la fin. Les builds sont rapides car Jamdesk ne pré-rend pas les pages. Votre contenu brut est envoyé vers l'edge, et les pages sont rendues à la demande lorsque les visiteurs les consultent.

<Steps>
  <Step title="Récupération de la source">
    Vous poussez vers votre branche GitHub connectée (ou cliquez sur Rebuild dans le dashboard). Jamdesk clone votre dépôt et localise votre répertoire de documentation.
  </Step>
  <Step title="Validation">
    Votre configuration `docs.json` est validée par rapport au schéma, et les liens internes sont vérifiés pour détecter les pages cassées et les ancres invalides.
  </Step>
  <Step title="Traitement du contenu">
    Jamdesk génère votre index de recherche, les embeddings du [chat IA](/fr/ai/chat), le sitemap, [`llms.txt`](/fr/ai/llms-txt) et les règles de redirection à partir de votre contenu.
  </Step>
  <Step title="Déploiement sur l'edge">
    Le contenu est envoyé vers le CDN et propagé sur plus de 300 emplacements edge. Seuls les fichiers modifiés sont transférés, donc les redéploiements sont rapides.
  </Step>
</Steps>

## Ce qui déclenche un build

Un git push vers votre branche connectée, le bouton Rebuild dans le dashboard, ou [`jamdesk deploy`](/fr/cli/deploy) depuis le CLI. Si vous poussez plusieurs commits en succession rapide, Jamdesk les regroupe en un seul build pour ne pas gaspiller de ressources.

Pour les détails opérationnels (surveillance du statut, rollbacks, variables d'environnement, déploiements de branches), consultez [Cycle de vie build et déploiement](/fr/deploy/lifecycle).

## Sécurité et infrastructure

Vous n'avez pas besoin d'y penser, mais si votre équipe sécurité pose la question : les builds s'exécutent dans des conteneurs isolés et votre connexion GitHub App est en lecture seule.

## Performance

La visibilité de votre documentation dépend en partie de sa vitesse de chargement. Google utilise les [Core Web Vitals](https://jamdesk.com/blog/why-google-pagespeed-matters) comme signal de classement, et les crawlers IA comme GPTBot et ClaudeBot s'accordent 1 à 5 secondes par page. Si votre documentation ne se charge pas dans ce délai, elle n'est pas citée.

Chaque site Jamdesk est servi depuis l'edge avec un délai jusqu'au premier octet inférieur à 50 ms. C'est suffisamment rapide pour les seuils de classement de Google et pour que les crawlers IA puissent récupérer et citer le contenu.

| Métrique | Valeur typique |
|--------|---------------|
| Temps de build | 30-60 secondes |
| Propagation du déploiement | < 30 secondes |
| Premier octet (edge) | < 50ms |
| Chargement complet de la page | < 500ms |
