Questions fréquentes sur les tarifs, les builds, les domaines et les fonctionnalités.

## Pour commencer

<AccordionGroup>
  <Accordion title="Qu'est-ce que Jamdesk ?">
    Jamdesk est une plateforme de documentation qui génère des sites de docs à partir de vos fichiers Markdown. Rédigez en MDX, poussez sur GitHub, et votre site se déploie automatiquement avec recherche, analytique et `llms.txt` prêt pour l'IA.
  </Accordion>

  <Accordion title="Dois-je savoir coder ?">
    Aucune compétence en développement n'est requise. Écrire en MDX ressemble à utiliser un éditeur de texte : vous rédigez du texte brut avec une mise en forme simple. Les composants sont disponibles si vous le souhaitez, mais ils sont entièrement facultatifs.
  </Accordion>

  <Accordion title="Puis-je essayer Jamdesk gratuitement ?">
    Oui ! Nous proposons un essai gratuit de 14 jours avec accès complet à toutes les fonctionnalités.
  </Accordion>

  <Accordion title="Quelle est la différence entre Jamdesk et les autres plateformes de documentation ?">
    Jamdesk est construit autour de MDX et GitHub : vos docs sont des fichiers texte brut dans un dépôt, non enfermés dans un éditeur propriétaire. Poussez sur GitHub et votre site se déploie en moins de 60 secondes, sans configuration de build ni pipeline CI/CD. Chaque site obtient automatiquement `llms.txt` et un serveur MCP, afin que les outils IA comme Claude et ChatGPT puissent accéder directement à vos docs actuelles. Les visiteurs bénéficient également d'un [assistant de chat IA intégré](/fr/ai/chat) qui répond aux questions à partir de vos docs.
  </Accordion>
</AccordionGroup>

## Builds et déploiement

<AccordionGroup>
  <Accordion title="Combien de temps prennent les builds ?">
    La plupart des sites de documentation se construisent en 30 à 60 secondes. Les sites plus volumineux avec de nombreuses pages peuvent prendre plus longtemps.
  </Accordion>

  <Accordion title="Puis-je prévisualiser les modifications avant de les publier ?">
    Oui ! Utilisez le CLI Jamdesk (`jamdesk dev`) pour prévisualiser localement avec rechargement à chaud. Les modifications ne sont mises en ligne que lorsque vous poussez sur GitHub ou exécutez `jamdesk deploy`.
  </Accordion>

  <Accordion title="Puis-je déployer sans GitHub ?">
    Oui. Exécutez `jamdesk deploy` depuis le répertoire de votre projet. Le CLI conditionne vos fichiers, les téléverse et déclenche un build directement. Aucun dépôt Git n'est requis. Consultez le [guide CLI Deploy](/fr/cli/deploy) pour plus de détails.
  </Accordion>

  <Accordion title="Qu'est-ce qui déclenche un build ?">
    Les builds se déclenchent automatiquement lorsque vous poussez vers votre branche GitHub connectée. Vous pouvez également déclencher des builds manuellement depuis le dashboard ou avec `jamdesk deploy` via le CLI.
  </Accordion>

  <Accordion title="Puis-je revenir à une version précédente ?">
    Oui. Accédez à **Déploiements** dans votre projet, trouvez le build précédent et cliquez sur **Rollback**.
  </Accordion>
</AccordionGroup>

## Domaines personnalisés

<AccordionGroup>
  <Accordion title="Puis-je utiliser mon propre domaine ?">
    Oui ! Ajoutez un domaine personnalisé dans **Paramètres** → **Domaines**. Les certificats SSL sont provisionnés automatiquement.
  </Accordion>

  <Accordion title="Combien de temps prend la propagation DNS ?">
    Les modifications DNS se propagent généralement en quelques heures, mais peuvent prendre jusqu'à 48 heures.
  </Accordion>

  <Accordion title="Puis-je héberger mes docs sur un sous-chemin comme /docs ?">
    Oui. Utilisez un reverse proxy (Cloudflare, AWS, nginx) pour servir Jamdesk sur un sous-chemin. Consultez [Hébergement sur sous-chemin](/fr/deploy/subpath-hosting).
  </Accordion>
</AccordionGroup>

## Équipes et collaboration

<AccordionGroup>
  <Accordion title="Comment inviter un membre d'équipe ?">
    Ouvrez votre projet, allez dans **Paramètres** → **Membres**, saisissez l'adresse e-mail de la personne dans le champ **Inviter un membre** et cliquez sur **Inviter**. Elle recevra un e-mail avec un lien pour rejoindre le projet.

    <Frame>
      <img src="/images/dashboard/settings-team.webp" alt="Members tab in project settings showing the Invite Member field and the current member list" style={{ display: 'block', margin: '0 auto' }} />
    </Frame>

    Les utilisateurs invités ont besoin d'un compte Jamdesk ; s'ils n'en ont pas, ils sont invités à en créer un lors de l'acceptation. Déjà membre, mais le lien d'invitation indique qu'il a « déjà été accepté » ? Vous n'avez pas besoin d'une nouvelle invitation. Connectez-vous simplement et vous serez redirigé vers le projet. Consultez [Membres de l'équipe](/fr/help/projects/team-members) pour les rôles et les limites de membres.
  </Accordion>

  <Accordion title="Combien de membres d'équipe puis-je avoir ?">
    Les plans Pro incluent 10 membres d'équipe par projet.
  </Accordion>

  <Accordion title="Les membres de l'équipe peuvent-ils modifier la documentation ?">
    Les membres de l'équipe peuvent consulter les builds et déclencher des reconstructions, mais la modification s'effectue dans votre dépôt GitHub. Toute personne ayant accès au dépôt peut modifier les docs.
  </Accordion>

  <Accordion title="Comment transférer la propriété du projet ?">
    Accédez à **Paramètres** → **Membres**, puis cliquez sur **Transférer la propriété** à côté du membre que vous souhaitez promouvoir. Le nouveau propriétaire doit être un membre existant de l'équipe.
  </Accordion>
</AccordionGroup>

## CLI

<AccordionGroup>
  <Accordion title="Où sont stockées mes identifiants CLI ?">
    Dans `~/.jamdeskrc`, un fichier JSON avec des permissions `0600` (seul votre utilisateur peut le lire). Il contient votre jeton de rafraîchissement, votre email et votre identifiant utilisateur. Exécutez `jamdesk logout` pour le supprimer.
  </Accordion>

  <Accordion title='Pourquoi le CLI indique-t-il "session expirée" ?'>
    Votre jeton de rafraîchissement n'est plus valide. Cela se produit après des changements de mot de passe, des suppressions de compte ou une inactivité prolongée. Exécutez `jamdesk login` pour obtenir une nouvelle session.
  </Accordion>

  <Accordion title="Puis-je utiliser le CLI dans des pipelines CI/CD ?">
    Oui, mais la connexion via navigateur ne fonctionnera pas dans les environnements sans interface graphique. Connectez-vous sur votre machine locale, puis copiez `~/.jamdeskrc` vers votre runner CI. Le jeton de rafraîchissement gère l'authentification à partir de là.
  </Accordion>

  <Accordion title="Comment corriger automatiquement les liens brisés ?">
    Exécutez `jamdesk fix`. La commande répare les liens internes brisés dont la cible correcte est non ambiguë — ancres avec fautes de frappe et dérive d'ancre cross-locale — en modifiant vos fichiers `.mdx` locaux après une prévisualisation. Utilisez `jamdesk fix --dry-run` pour voir les corrections planifiées en premier ; seuls les liens dont l'ancre corrigée est un titre réel sont modifiés, les cas ambigus restant à votre charge. Voir [Corriger automatiquement les liens brisés](/fr/cli/fix-broken-links).
  </Accordion>
</AccordionGroup>

## Contenu et fonctionnalités

<AccordionGroup>
  <Accordion title="Quels formats de fichiers sont pris en charge ?">
    Jamdesk prend en charge MDX (Markdown + JSX) et les fichiers Markdown standard.
  </Accordion>

  <Accordion title="Puis-je utiliser des composants React personnalisés ?">
    Oui. Définissez des composants inline directement dans MDX avec `export const`, ou créez des composants réutilisables dans le répertoire `/snippets`. Pour les composants interactifs avec des hooks, utilisez des fichiers `.tsx` avec `'use client'`. Consultez [Composants React personnalisés](/fr/content/react-components) et [Snippets](/fr/content/snippets).
  </Accordion>

  <Accordion title="Y a-t-il une limite de pages ?">
    Aucune limite stricte sur le nombre de pages. La plupart des sites de documentation fonctionnent bien avec des centaines de pages.
  </Accordion>

  <Accordion title="Jamdesk prend-il en charge plusieurs langues ?">
    Oui. Utilisez la propriété `languages` dans votre configuration de navigation pour créer un sélecteur de langue. Chaque langue dispose de sa propre structure de navigation et de son propre contenu. Consultez [Support multilingue](/fr/setup/languages).
  </Accordion>

  <Accordion title="Jamdesk traduit-il mon contenu automatiquement ?">
    Non. Jamdesk ne traduit pas le contenu à votre place. Vous fournissez les fichiers MDX traduits et Jamdesk gère le routage, la navigation, le sélecteur de langue et le style RTL. Apportez les traductions de votre propre workflow (traducteurs humains, traduction automatique ou un LLM) et placez-les dans des répertoires préfixés par la langue (`es/`, `fr/`, etc.). Consultez [Support multilingue](/fr/setup/languages) pour la structure des répertoires et la configuration.
  </Accordion>
</AccordionGroup>

## Chat IA

<AccordionGroup>
  <Accordion title="Mon site de documentation dispose-t-il du chat IA ?">
    Oui. Chaque site Jamdesk inclut un assistant de chat intégré qui répond aux questions des visiteurs à partir de votre documentation. Il est activé par défaut, aucune configuration n'est requise. Consultez [Chat IA](/fr/ai/chat) pour plus de détails.
  </Accordion>

  <Accordion title="Le chat IA est-il payant en supplément ?">
    Non. Le chat IA est inclus dans tous les plans sans coût supplémentaire.
  </Accordion>

  <Accordion title="Puis-je désactiver le chat IA ?">
    Oui. Définissez `chat.enabled` à `false` dans votre `docs.json` :

    ```json
    { "chat": { "enabled": false } }
    ```

    Le panneau de chat et le raccourci clavier seront supprimés après votre prochain build.
  </Accordion>

  <Accordion title="Quelles données le chat utilise-t-il pour répondre aux questions ?">
    Le chat utilise uniquement vos pages de documentation publiées. À chaque build, Jamdesk indexe votre contenu dans une base de données vectorielle. Lorsqu'un visiteur pose une question, les sections pertinentes sont récupérées et envoyées à Claude comme contexte. L'IA ne peut pas accéder à des données extérieures à vos docs.
  </Accordion>
</AccordionGroup>

## Confidentialité et accès

<AccordionGroup>
  <Accordion title="Puis-je avoir des docs publics et privés sur le même site ?">
    Oui. Marquez les pages internes avec `private: true` dans le frontmatter, ou listez leurs chemins sous `auth.password.private[]` dans `docs.json`. Les pages publiques restent publiques ; les pages privées affichent un écran de déverrouillage. Un seul projet, un seul dépôt, un seul build. Consultez [Contrôle d'accès](/fr/setup/access-control) et [Protection par mot de passe](/fr/setup/password-protection).
  </Accordion>

  <Accordion title="Comment verrouiller l'intégralité de mon site de documentation par un mot de passe ?">
    Définissez `auth.password.enabled: true` dans `docs.json`, poussez la modification, puis définissez un mot de passe dans **Paramètres du projet → Protection par mot de passe** dans le dashboard. Chaque visiteur voit un écran de déverrouillage jusqu'à ce qu'il le saisisse. Consultez [Protection par mot de passe](/fr/setup/password-protection).
  </Accordion>

  <Accordion title="Les lecteurs peuvent-ils se connecter avec leur propre compte plutôt qu'un mot de passe partagé ?">
    Oui, sur les plans Enterprise. L'authentification unique (SSO) permet aux lecteurs de s'authentifier auprès de votre fournisseur d'identité (Okta, Google Workspace, Azure AD, etc.) sans mots de passe partagés, avec un journal d'audit complet et une révocation instantanée des accès. Consultez [SSO](/fr/setup/sso) ou [contactez les ventes Enterprise](https://jamdesk.com/pricing).
  </Accordion>

  <Accordion title="Dois-je séparer les docs internes et externes en deux projets ?">
    En général, non. Un seul projet avec `private: true` sur les pages internes est plus simple : même dépôt, même build, un seul dashboard. Utilisez deux projets uniquement lorsque les audiences nécessitent un branding entièrement distinct, des domaines personnalisés ou des analytiques séparées. Consultez [Contrôle d'accès](/fr/setup/access-control) pour les modèles disponibles.
  </Accordion>

  <Accordion title="Quelle est la différence entre un éditeur et un lecteur ?">
    Les **éditeurs** rédigent les docs en soumettant du MDX dans votre dépôt GitHub connecté : toute personne ayant un accès en écriture à votre branche de documentation peut publier une modification. Les **lecteurs** consultent le site publié : tout le monde (public), toute personne disposant du mot de passe (mode mot de passe), ou toute personne connectée via votre fournisseur d'identité (SSO). Les **membres de l'équipe du dashboard** sont un concept distinct : ils gèrent les builds et les analytiques, mais ne rédigent pas de contenu directement. Consultez [Contrôle d'accès](/fr/setup/access-control).
  </Accordion>
</AccordionGroup>
