Lorsqu'un build se termine avec des liens rompus ou des pages sans description, Jamdesk peut en réparer beaucoup pour vous. Le bouton **Fix with AI** lit ces avertissements de build, propose une modification concrète pour chacun d'eux, et commite les corrections que vous approuvez dans votre dépôt GitHub connecté, ce qui déclenche un nouveau build. Cette page s'adresse à toute personne qui maintient un site Jamdesk et souhaite résoudre les avertissements de build sans modifier le MDX à la main.

Les captures d'écran montrent l'interface en anglais.

Pour une version locale, basée sur le terminal, de la même idée, consultez la [commande CLI `jamdesk fix`](/fr/cli/fix-broken-links). Le flux du dashboard ci-dessous commite les modifications pour vous ; la CLI écrit dans votre copie de travail et vous laisse effectuer le commit.

## Ce qu'il corrige

Fix with AI fonctionne avec trois types d'avertissement de build :

- **Liens internes rompus.** Un fragment de lien qui pointe vers un titre qui n'existe plus sur la page cible, comme une faute de frappe (`#instalation` → `#installation`), ou une page traduite dont le titre a été renommé.
- **Descriptions de page manquantes.** Une page sans `description` dans son frontmatter. Jamdesk rédige un court résumé à partir du contenu de la page, pour que vous puissiez le relire.
- **Titres de page manquants.** Une page sans titre reçoit une suggestion, basée sur le contenu de la page, à valider par vous.

Il ne propose une modification que lorsqu'il peut résoudre la cible avec certitude. Tout ce qui reste ambigu n'est pas modifié et est listé séparément afin que vous puissiez le corriger vous-même.

<Note>
  Le nombre d'éléments corrigibles n'est pas le même que le nombre d'avertissements. Un build peut afficher cinq avertissements alors que Fix with AI propose d'en corriger trois, car les deux autres n'ont pas de correction non ambiguë. La bannière reflète toujours ce qui peut réellement être corrigé.
</Note>

## Prérequis

- Un [dépôt GitHub connecté](/fr/integrations/github) pour le projet.
- Un accès en écriture pour l'application GitHub de Jamdesk, afin qu'elle puisse commiter les corrections. Si l'accès est manquant, la fenêtre modale affiche un lien **Grant access** qui vous redirige vers GitHub pour l'ajouter.
- Un build terminé comportant des avertissements de lien rompu ou de description manquante.

## Repérer la bannière

Ouvrez votre projet et faites défiler jusqu'à **Build History** sur la page Project Home. Lorsque votre dernier build comporte des problèmes corrigibles, une bannière apparaît au-dessus de la liste des builds, avec un nombre et un bouton **Fix with AI**.

La bannière n'apparaît que sur votre build terminé le plus récent. Les builds plus anciens de l'historique ne l'affichent pas, car les corrections s'appliquent toujours à l'état actuel de votre documentation.

## Passer en revue et appliquer les corrections

<Steps>
  <Step title="Ouvrir la preview">
    Cliquez sur **Fix with AI**. La fenêtre modale s'ouvre et l'agent IA analyse votre documentation pour établir un plan de correction. Cela prend quelques secondes.
  </Step>
  <Step title="Lire chaque modification proposée">
    Les corrections sont regroupées par type. **Broken links** affiche chaque ancre réécrite, **Missing descriptions** affiche le résumé suggéré pour chaque page, et **Missing titles** affiche le titre proposé. Décochez tout ce que vous préférez ignorer pour cette fois, ou utilisez le bouton d'ignorer pour [faire taire une recommandation définitivement](#ignorer-les-recommandations). Les problèmes sans correction claire apparaissent sous **Can't be fixed automatically** et sont laissés pour que vous les traitiez vous-même.

    <Frame>
      <img src="/images/fix-with-ai/modal.webp" alt="La fenêtre modale Fix with AI. Une section Broken links liste trois corrections cochées, chacune montrant l'ancienne ancre barrée et l'ancre corrigée. Une section Can't be fixed automatically liste deux problèmes à corriger manuellement, au-dessus des boutons Cancel et Apply 3 fixes." />
    </Frame>
  </Step>
  <Step title="Appliquer">
    Cliquez sur **Apply fixes**. Jamdesk commite les modifications sélectionnées dans votre branche connectée avec le message `docs: apply AI-suggested fixes (via Jamdesk)` et démarre un nouveau build.
  </Step>
  <Step title="Confirmer la reconstruction">
    Suivez le nouveau build dans [Build History](/fr/builds/monitoring). Une fois qu'il est en ligne, les avertissements corrigés ont disparu. Ce qu'il reste est soit un avertissement que Fix with AI n'a pas pu résoudre, soit un nouveau problème lié au contenu le plus récent.
  </Step>
</Steps>

<Note>
  L'application écrit un véritable commit dans votre dépôt, de sorte que la modification est suivie dans votre historique Git et que vous pouvez la relire ou l'annuler sur GitHub comme n'importe quel autre commit.
</Note>

## Lorsque certains problèmes ne peuvent pas être corrigés

Si un avertissement n'a pas de correction claire, la fenêtre modale le liste sous un titre séparé et le laisse tel quel. Raisons courantes :

- Un lien rompu dont la page ou le titre cible n'existe nulle part, de sorte qu'il n'y a rien vers quoi le faire pointer.
- Une entrée de navigation sans fichier source correspondant.
- Une page pour laquelle l'agent n'a pas pu générer de description automatiquement.

Ces cas nécessitent une modification manuelle. Ouvrez la page dans l'[éditeur](/fr/development/local-preview) ou votre éditeur de code, corrigez le lien ou ajoutez la description, puis effectuez un push pour relancer un build.

## Ignorer les recommandations

Certains avertissements ne méritent pas d'action : un lien que vous avez cassé volontairement, ou une page ébauche qui n'a pas besoin de description. Décocher une correction ne fait que l'ignorer une fois. L'ignorer la retire du décompte jusqu'à ce que vous décidiez du contraire.

Chaque ligne de la fenêtre modale, corrigible ou non, dispose d'un bouton d'ignorer. Cliquez dessus et l'élément passe dans une section **Ignored** repliée, en bas. Une fois la fenêtre modale fermée, le nombre affiché dans la bannière sur la page Project Home diminue en conséquence, et les avertissements correspondants disparaissent de Build History, sur le build actuel et sur tous les builds suivants. **Ignore all** fait de même pour tout ce qui reste listé.

Comportement des éléments ignorés :

- **Partagé et persistant.** Les éléments ignorés s'appliquent à l'ensemble du projet, de sorte que chaque membre voit la même liste, et cela se maintient d'un build à l'autre. Jamdesk associe chaque avertissement à son contenu plutôt qu'à son numéro de ligne, donc modifier d'autres parties de la page ne fera pas réapparaître un élément ignoré.
- **Restauration.** Développez la section **Ignored** et cliquez sur **Restore** sur n'importe quel élément. Si vous ignorez tout sur un build, la bannière disparaît et un petit lien « N ignored recommendations » sous Build History rouvre la fenêtre modale.
- **Les avertissements modifiés reviennent.** Si le problème sous-jacent change, par exemple si le lien rompu pointe désormais ailleurs, il ne correspond plus à l'entrée ignorée et réapparaît comme une nouvelle recommandation.

## Fix with AI face à la CLI

Les deux outils corrigent les ancres de liens rompus. Ils diffèrent par leur environnement d'exécution et la façon dont la modification est appliquée.

| | Fix with AI (dashboard) | [`jamdesk fix`](/fr/cli/fix-broken-links) (CLI) |
|---|---|---|
| Exécution | Dans le dashboard, sur un build | Dans votre terminal, sur les fichiers locaux |
| Corrections | Liens rompus et descriptions manquantes | Ancres de liens rompus |
| Commit | Commite dans votre branche pour vous | Écrit dans les fichiers locaux ; vous commitez |
| Déclenchement | Un clic sur la bannière du build | `jamdesk fix` |

Utilisez le flux du dashboard pour une correction rapide sans quitter Jamdesk. Utilisez la CLI lorsque vous voulez d'abord avoir les modifications dans votre copie de travail, par exemple pour les regrouper avec d'autres modifications.
