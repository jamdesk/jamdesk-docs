## Optimiser votre contenu

### Rédiger un frontmatter efficace

```yaml
---
title: User Authentication    # Under 60 characters
description: Set up OAuth, JWT, and session-based authentication  # 120-160 characters
---
```

<Tip>
**Placez les mots-clés en premier.** « Authentication setup » est préférable à « How to set up authentication ».
</Tip>

### Titres de page

- Restez sous 60 caractères, en comptant le nom du site que le format de titre ajoute, pour éviter la troncature dans les résultats de recherche
- Placez votre mot-clé principal près du début
- Assurez-vous que chaque titre est unique dans votre documentation

Par défaut, le titre de l'onglet du navigateur et des résultats de recherche est `Titre de la page — Nom du site`. Pour le modifier, définissez `seo.titleTemplate` dans `docs.json`. Placez `%s` à l'endroit où le titre de la page doit apparaître :

```json
{
  "seo": {
    "titleTemplate": "%s | Acme"
  }
}
```

Une page intitulée `Getting started` affiche alors `Getting started | Acme`. Utilisez `"%s"` seul pour omettre le nom du site. Si le modèle ne contient pas `%s`, le build échoue et `jamdesk validate` affiche l'erreur. Les aperçus de liens (`og:title` et `twitter:title`) affichent toujours le titre de la page seul.

Deux types de pages n'utilisent pas le modèle. Une page sans `title` affiche votre `name` suivi de « Documentation », par exemple `Acme Documentation`, ou simplement votre `name` s'il se termine déjà par « Docs » ou « Documentation ». Une page dont le titre est identique à votre `name` affiche ce titre seul.

`jamdesk validate` et `jamdesk dev` acceptent `seo.titleTemplate` à partir de la version 1.1.220 de la CLI. Mettez à jour avec `npm i -g jamdesk@latest`.

### Descriptions

- Visez 120 à 160 caractères
- Résumez ce que le lecteur va apprendre
- Intégrez naturellement des mots-clés pertinents

<Note>
**Repli automatique.** Lorsque `description` est absent du frontmatter, Jamdesk extrait automatiquement le premier paragraphe de prose du contenu de la page (jusqu'à 155 caractères). Les titres, blocs de code, images et composants MDX sont ignorés. Ceci est utilisé pour `<meta name="description">`, Open Graph et les Twitter cards. Rédiger une description explicite reste recommandé pour de meilleurs résultats.
</Note>

## Contrôler l'indexation

### Paramètres à l'échelle du site

Dans votre `docs.json`, configurez le comportement par défaut des robots :

```json docs.json
{
  "seo": {
    "metatags": {
      "robots": "index, follow"
    }
  }
}
```

### Contrôle par page

Remplacez l'indexation pour des pages spécifiques dans le frontmatter :

```yaml
---
title: Internal Notes
noindex: true
---
```

Utilisez `noindex` pour :
- Les pages en brouillon ou en cours de rédaction
- La documentation interne
- Le contenu obsolète que vous conservez pour référence

### Indexation de recherche vs. ingestion par l'IA

Les métadonnées `robots` et `noindex` contrôlent les **moteurs de recherche** : si une page apparaît dans Google et dans votre `sitemap.xml`. Elles n'ont aucun effet sur les fichiers `llms.txt` et `llms-full.txt` lus par les outils d'IA. Pour arrêter de publier ces fichiers, définissez `seo.ai.llmsTxt` sur `false` (voir [Désactiver llms.txt](/fr/ai/llms-txt#désactiver-llmstxt)). Les deux contrôles sont indépendants : une page peut être indexée par les moteurs de recherche mais exclue de l'ingestion par l'IA, ou l'inverse.

## URLs canoniques

Si votre documentation est accessible via plusieurs URLs, définissez une URL canonique :

```yaml
---
title: Getting Started
canonical: https://docs.example.com/getting-started
---
```

Vous pouvez également définir une base canonique à l'échelle du site dans `docs.json`. Jamdesk ajoute
le chemin de chaque page à cette base, afin que chaque page obtienne une URL canonique correcte :

```json docs.json
{
  "seo": {
    "metatags": {
      "canonical": "https://docs.acme.com"
    }
  }
}
```

## Aperçus sociaux et Open Graph

Jamdesk génère automatiquement une carte sociale 1200×630 à l'image de votre marque pour chaque page. Remplacez
n'importe quelle balise sociale dans le frontmatter. Vous pouvez utiliser des **clés plates de premier niveau** ou un
bloc **`seo:`** imbriqué. Les deux fonctionnent, et lorsque la même clé est définie des deux façons, la valeur plate
de premier niveau l'emporte.

<Card title="OpenGraph Preview" icon="share-nodes" href="https://jamdesk.com/utilities/opengraph-preview" horizontal>
  Découvrez comment la carte de n'importe quelle page s'affiche sur X, Facebook, LinkedIn et plus encore, et validez ses balises Open Graph, avec l'outil OpenGraph Preview.
</Card>

<CodeGroup>
```yaml Flat (top-level)
---
title: API Reference
description: REST API endpoints and authentication
"og:title": API Reference — Acme
"og:description": Everything you need to call the Acme API
"og:image": /images/api-social-card.png
"twitter:card": summary_large_image
"twitter:creator": "@acme"
keywords: ["api", "rest", "authentication"]
canonical: https://docs.acme.com/api-reference
---
```

```yaml Nested (seo block)
---
title: API Reference
description: REST API endpoints and authentication
seo:
  "og:title": API Reference — Acme
  "og:image": /images/api-social-card.png
  "twitter:card": summary_large_image
  x-custom-tag: any custom meta value
---
```
</CodeGroup>

### Balises prises en charge

| Groupe | Balises |
|-------|------|
| Open Graph | `og:title`, `og:description`, `og:image`, `og:image:width`, `og:image:height`, `og:image:alt`, `og:url`, `og:type`, `og:site_name`, `og:locale`, `og:video`, `og:audio` |
| Article | `og:type: article` avec `article:published_time`, `article:modified_time`, `article:author`, `article:section`, `article:tag` |
| Twitter / X | `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image`, `twitter:image:alt`, `twitter:site`, `twitter:creator`, `twitter:player`, balises app-card |
| Autre | `keywords`, `author`, `robots`, `googlebot`, `google-site-verification`, `theme-color`, plus toute balise personnalisée (placez les balises personnalisées sous `seo:`) |

<Note>
**Dimensions personnalisées d'image OG.** `og:image:width` et `og:image:height` ne s'appliquent que lorsque
[`customImage`](#personnaliser-la-carte-sociale) vaut `"replace"`. Définissez-les au même endroit que
le `og:image` qu'elles décrivent, soit dans le frontmatter de la page, soit dans `seo.metatags`. La carte
générée fait toujours 1200×630.
</Note>

<Note>
**Balises personnalisées.** Les balises meta arbitraires (par ex. `x-pinterest`) sont émises comme `<meta name="...">`.
Placez-les sous le bloc `seo:`. Seules les clés SEO reconnues sont prises en compte lorsqu'elles sont placées à plat.
</Note>

### Type de carte Twitter / X

La balise `twitter:card` contrôle la mise en page que X (et d'autres plateformes) utilise lorsque votre lien est partagé :

| Valeur | À quoi ça ressemble |
|-------|--------------------|
| `summary` | Petite vignette carrée à gauche, titre + description à côté. Compact. |
| `summary_large_image` | Grande image pleine largeur en haut, titre + description en dessous. La version marquante et attractive. |

Pour une carte à l'image de la marque en 1200×630, utilisez `summary_large_image` afin que l'image s'affiche en pleine largeur.

### Image par défaut à l'échelle du site

Définissez une image sociale de repli pour chaque page dans `docs.json`. Toute page qui définit son propre `og:image` la remplace :

```json docs.json
{
  "seo": {
    "metatags": {
      "og:image": "https://docs.acme.com/images/default-card.png"
    }
  }
}
```

<Tip>
**Prévisualisez avant de publier.** Après un build, collez l'URL de la page dans l'outil [OpenGraph Preview](https://jamdesk.com/utilities/opengraph-preview) pour vérifier le rendu de la carte sur chaque plateforme et valider les balises Open Graph. Il vérifie aussi les dimensions de l'image et explique comment corriger les problèmes détectés.
</Tip>

### Personnaliser la carte sociale

Votre carte générée garde son apparence actuelle, sauf si vous ajoutez `seo.socialCard` à `docs.json`.
Ne définissez que les clés que vous souhaitez modifier :

```json docs.json
{
  "seo": {
    "socialCard": {
      "theme": "dark",
      "brandColor": true,
      "accentBar": false,
      "siteName": false,
      "customImage": "replace"
    }
  }
}
```

| Clé | Par défaut | Effet |
|-----|---------|--------|
| `theme` | `"light"` | `"dark"` utilise un texte clair sur un fond sombre et votre image `logo.dark`. |
| `brandColor` | `false` | `true` colore la barre du bas et le badge de section avec `colors.primary`. Une carte sombre utilise `colors.light` si vous l'avez défini. Si vous n'avez pas de `colors`, la carte utilise la couleur d'accent de votre thème. `false` conserve le rouge par défaut. |
| `accentBar` | `true` | `false` supprime la barre colorée en bas de la carte. |
| `siteName` | `true` | `false` masque le nom du site sous le logo. Utilisez-le lorsque votre logo affiche déjà le nom. |
| `customImage` | `"background"` | `"background"` dessine le titre de la page par-dessus votre `og:image`. `"replace"` utilise votre `og:image` comme carte entière. |

La carte ne peut dessiner que des logos SVG, PNG et JPG. Jamdesk convertit en WebP les fichiers de logo PNG et JPG
de votre dépôt lors du build de votre site, si bien que la carte affiche généralement votre favicon à la place et
conserve le nom du site, même avec `siteName: false`. Utilisez un logo SVG pour afficher votre logo complet sur la
carte, et `logo.dark` sur une carte sombre.

La carte ne peut pas dessiner le texte d'un logo SVG : le texte reste donc vide. Pour corriger cela, convertissez le texte en contours (tracés) dans votre outil de conception, puis exportez de nouveau le SVG. Dans Figma, sélectionnez le texte et utilisez **Flatten**. Dans Illustrator, utilisez **Type > Create Outlines**. Votre build affiche une suggestion quand il trouve du texte dans le logo SVG utilisé par la carte. Les logos indiqués par une URL complète (`https://...`) ne sont pas vérifiés.

Si votre couleur de marque ne ressort pas assez sur la carte, le texte du badge utilise la couleur de texte
normale à la place. La barre conserve votre couleur de marque, sauf si cette couleur est presque identique au fond
de la carte. Dans ce cas, la barre est grise.

Par défaut, Jamdesk dessine le titre de la page par-dessus votre `og:image`. Si votre image contient déjà
son propre texte ou son propre design, définissez `"customImage": "replace"` pour l'afficher telle quelle.

Lorsque votre `og:image` sert de fond à la carte, choisissez le `theme` qui lui correspond : `dark` pour une
image sombre, `light` pour une image claire.

En mode `replace`, Jamdesk ne dessine aucun titre sur l'image. Si `seo.metatags` définit `og:image`,
toutes les pages utilisent cette image, et une page qui définit son propre `og:image` utilise celle-ci à la place.
Seules les pages qui n'ont ni l'un ni l'autre obtiennent une carte générée. Utilisez un PNG ou un JPG de 1200×630.
Certaines plateformes n'affichent pas les images WebP ou SVG.

Les réseaux sociaux mettent en cache les aperçus de liens : un lien déjà partagé peut donc conserver l'ancienne carte
pendant un certain temps après la modification de ces paramètres. Vérifiez la nouvelle carte avec l'outil
[OpenGraph Preview](https://jamdesk.com/utilities/opengraph-preview).

<Note>
Les anciennes versions de la CLI Jamdesk rejettent `seo.socialCard` et `seo.titleTemplate` dans
`jamdesk validate` et `jamdesk dev`. Mettez à jour avec `npm i -g jamdesk@latest`.
</Note>

## Sitemap et Robots.txt

Chaque site Jamdesk génère automatiquement `sitemap.xml` et `robots.txt` à chaque build.

| Fichier | Objectif |
|------|---------|
| `sitemap.xml` | Répertorie toutes les pages avec leurs dates de dernière modification pour les moteurs de recherche |
| `robots.txt` | Autorise tous les robots d'indexation et les oriente vers le sitemap |

### Où les trouver

Les URLs dépendent du fait que votre documentation se trouve à la racine d'un domaine ou sous un sous-chemin `/docs` :

<Tabs>
  <Tab title="Domaine racine">
    Si votre documentation se trouve à la racine de votre domaine (par ex. `docs.acme.com` ou `acme.jamdesk.app`) :

    ```bash
    https://docs.acme.com/sitemap.xml
    https://docs.acme.com/robots.txt
    ```
  </Tab>
  <Tab title="Sous-chemin /docs">
    Si votre documentation se trouve sous `/docs` sur votre site principal (comme ce site sur `jamdesk.com/docs`) :

    ```bash
    https://jamdesk.com/docs/sitemap.xml
    https://jamdesk.com/docs/robots.txt
    ```
  </Tab>
</Tabs>

### Ce qui est inclus dans le sitemap

- Toutes les pages publiées (à l'exclusion de celles avec `noindex` ou `hidden` dans le frontmatter)
- Les dates de dernière modification du frontmatter lorsqu'elles sont disponibles
- Une fréquence de changement hebdomadaire

### Exclure des pages du sitemap

Ajoutez `noindex` au frontmatter pour exclure une page à la fois du sitemap et des moteurs de recherche :

```yaml
---
title: Internal Notes
noindex: true
---
```

Les pages avec `hidden: true` sont également exclues automatiquement.

## Données structurées JSON-LD

Chaque page inclut automatiquement des données structurées [schema.org](https://schema.org) sous forme de balise `<script type="application/ld+json">` avec deux schémas :

- `WebSite` : le nom, l'URL et la description de votre site (depuis `docs.json`).
- `BreadcrumbList` : le chemin de navigation depuis l'accueil jusqu'à la page actuelle, dérivé de votre configuration `navigation`.

Aucune configuration nécessaire. Les moteurs de recherche utilisent ces données pour des résultats enrichis comme les fils d'Ariane dans les listes de recherche.

<Tip>
**Vérifiez votre balisage.** Collez l'URL de n'importe quelle page dans le [Rich Results Test de Google](https://search.google.com/test/rich-results) pour confirmer que les données structurées sont détectées.
</Tip>

## IndexNow

Après chaque build, Jamdesk soumet automatiquement les URLs de pages modifiées à [IndexNow](https://www.indexnow.org) pour une indexation plus rapide par les moteurs de recherche. Cela informe Bing, Yandex et d'autres moteurs de recherche participants des changements de votre contenu sans attendre leur prochain cycle d'exploration.

- Se déclenche après chaque build réussi
- Ne soumet que les pages qui ont réellement changé
- Non bloquant, donc ne retarde jamais votre build
- Aucune configuration requise

## Bonnes pratiques

Passez en revue cette checklist avant de publier :

<Note>
**Checklist avant publication**

- **Titres uniques.** Chaque page a un titre distinct et descriptif de moins de 60 caractères.
- **Descriptions précises.** Les descriptions résument la page en 120 à 160 caractères.
- **Titres logiques.** Les titres suivent une hiérarchie claire : un seul H1, puis H2 → H3.
- **Liens descriptifs.** Les liens internes utilisent un texte d'ancrage significatif, jamais « cliquez ici ».
- **Texte alternatif des images.** Chaque image a un texte alternatif pour l'accessibilité et la recherche d'images.
- **Image sociale.** Définissez un `og:image` personnalisé sur les pages clés, ou fiez-vous à la carte générée automatiquement. Vérifiez-la avec l'outil [OpenGraph Preview](https://jamdesk.com/utilities/opengraph-preview).
</Note>
