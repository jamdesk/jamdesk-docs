O Jamdesk cria sites de documentação a partir de arquivos MDX no seu repositório do GitHub. Você escreve em Markdown com componentes React, envia as alterações para o GitHub e publica seu site em uma CDN global em menos de 60 segundos. Seu conteúdo permanece no repositório como arquivos MDX simples, para que você possa migrá-lo para outra ferramenta a qualquer momento.

## Visão geral da arquitetura

Seu repositório é a fonte da verdade. O Jamdesk se conecta a ele, cria seu site e o implanta em uma rede global de edge. Você não precisa gerenciar nenhuma infraestrutura.

## O pipeline de build

Normalmente, do início ao fim, leva de 30 a 60 segundos. Os builds são rápidos porque o Jamdesk não pré-renderiza as páginas. Seu conteúdo bruto vai para a edge, e as páginas são renderizadas sob demanda quando os visitantes as solicitam.

<Steps>
  <Step title="Obter o código-fonte">
    Envie alterações para sua branch conectada do GitHub (ou clique em Rebuild no painel). O Jamdesk clona seu repositório e localiza o diretório de documentação.
  </Step>
  <Step title="Validação">
    A configuração `docs.json` é validada de acordo com o esquema, e os links internos são verificados para detectar páginas inexistentes e âncoras inválidas.
  </Step>
  <Step title="Processamento do conteúdo">
    O Jamdesk gera, a partir do seu conteúdo, o índice de busca, os embeddings do [chat com IA](/pt/ai/chat), o mapa do site, o arquivo [`llms.txt`](/pt/ai/llms-txt) e as regras de redirecionamento.
  </Step>
  <Step title="Implantação na edge">
    O conteúdo é enviado para a CDN e distribuído por mais de 300 localidades de edge. Somente os arquivos alterados são transferidos, então as reimplantações são rápidas.
  </Step>
</Steps>

## O que aciona um build

Um push do Git para sua branch conectada, o botão Rebuild no painel ou [`jamdesk deploy`](/pt/cli/deploy) pela CLI. Se você enviar vários commits em sequência rápida, o Jamdesk os agrupa em um único build para evitar o uso desnecessário de recursos.

Para ver detalhes operacionais (monitoramento de status, reversões e implantações de branches), consulte [Ciclo de build e implantação](/pt/deploy/lifecycle).

## Segurança e infraestrutura

Você não precisa se preocupar com isso, mas, se sua equipe de segurança perguntar: os builds são executados em contêineres isolados, e a conexão do GitHub App é somente para leitura.

<Columns cols={2}>
  <Card title="Permissões mínimas" icon="shield-check">
    O GitHub App solicita acesso somente de leitura aos repositórios que você selecionar. O app não tem acesso de gravação e não solicita permissões para toda a organização.
  </Card>
  <Card title="Builds isolados" icon="box">
    Cada build recebe seu próprio contêiner, que é destruído após a implantação. Nada persiste entre builds ou clientes.
  </Card>
  <Card title="HTTPS em todos os lugares" icon="lock">
    Certificados SSL automáticos para domínios personalizados e subdomínios. Os certificados são emitidos e renovados automaticamente.
  </Card>
  <Card title="CDN global" icon="globe">
    Conteúdo servido pela rede da Cloudflare, com mais de 300 localidades de edge e 99,9% de disponibilidade.
  </Card>
</Columns>

## Desempenho

A rapidez de carregamento influencia a descoberta da sua documentação. O Google usa [Core Web Vitals](https://jamdesk.com/blog/why-google-pagespeed-matters) como sinal de classificação, e rastreadores de IA como GPTBot e ClaudeBot reservam de 1 a 5 segundos por página. Se sua documentação não carregar nesse intervalo, ela não será citada.

Todos os sites Jamdesk são servidos pela edge, com tempo até o primeiro byte inferior a 50 ms. Isso é rápido o suficiente para atender aos limites de classificação do Google e permitir que rastreadores de IA acessem e citem seu conteúdo.

| Métrica | Valor típico |
|--------|---------------|
| Tempo de build | 30-60 segundos |
| Propagação da implantação | < 30 segundos |
| Primeiro byte (edge) | < 50ms |
| Carregamento completo da página | < 500ms |
