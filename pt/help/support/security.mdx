Como a Jamdesk protege sua documentação e os dados da sua conta.

## Segurança da infraestrutura

### Hospedagem

A Jamdesk funciona em provedores de nuvem em conformidade com SOC 2. Os builds, os dados da aplicação e a documentação compilada ficam em serviços gerenciados e protegidos desses provedores. Uma CDN global com proteção contra DDoS integrada distribui o tráfego.

### Criptografia

| Estado dos dados | Proteção |
|------------|------------|
| Em trânsito | TLS 1.3 entre você, nossa borda e nossas origens |
| Em repouso | AES-256 para tudo o que armazenamos, incluindo registros do banco de dados, armazenamento de objetos e logs |
| Backups | Criptografados com as mesmas chaves e replicados em várias regiões |

## Controles de acesso

### Login

Você pode entrar no painel com e-mail e senha ou com login único pelo Google ou GitHub. Nosso provedor de autenticação mantém apenas hashes unidirecionais de senhas, nunca senhas em texto simples.

A MFA na sua conta do Google ou GitHub (TOTP, chaves de segurança, chaves de acesso) também se aplica ao login na Jamdesk por essa conta. Para obter a proteção mais forte, ative a MFA lá e entre com SSO.

### Acesso da equipe

O acesso baseado em funções (Owner, Admin, Member) é aplicado pelas regras de segurança do nosso banco de dados e em cada chamada ao backend. As sessões expiram após períodos de inatividade. Alterações no faturamento, nos membros, nos domínios personalizados ou nas chaves de API são registradas em um log de auditoria por projeto.

### Integração com GitHub

A Jamdesk se conecta aos seus repositórios por meio de um GitHub App com estas permissões:

- Acesso de leitura e gravação ao conteúdo dos repositórios
- Entrega de Webhook para acionar builds

A Jamdesk só grava no seu repositório quando você solicita: ao salvar alterações no editor do painel, aceitar sugestões de Fix with AI ou ativar a tradução (que faz commit das páginas traduzidas). Os builds só leem. Revogue o acesso da Jamdesk a qualquer momento nas [configurações de Applications](https://github.com/settings/installations) do GitHub.

### Tokens e segredos

Criptografamos todos os segredos em repouso, incluindo:

- Conexões do GitHub App, para as quais mantemos apenas o ID numérico da instalação. Os tokens de instalação de curta duração (válidos por uma hora) são gerados sob demanda e nunca persistidos.
- Tokens OAuth do GitHub do fluxo de repositório inicial. Trocamos cada token uma única vez, usamos para clonar o modelo e o descartamos.
- Credenciais de integrações de terceiros, como URLs de Webhook de entrada do Slack, tokens de verificação de domínio personalizado e chaves de API de análise.

Depois de salvar, o painel nunca retorna esses valores ao navegador. Somente o pipeline de build do lado do servidor pode lê-los.

As chaves de API programáticas são armazenadas como hashes unidirecionais. O valor em texto simples é exibido para você apenas uma vez, no momento da criação. Se você o perder, gere uma nova chave.

## Tratamento de dados

### O que armazenamos

- Sua configuração `docs.json` e todos os recursos de marca enviados
- Documentação compilada (HTML, CSS, JS)
- Logs de build, mantidos por 30 dias
- Eventos de visualização de página do seu site de documentação (caminho, referenciador, país, navegador, tipo de dispositivo e ID de sessão por aba), excluídos após 90 dias. As visualizações de página registradas desde 14 de outubro de 2026 não incluem endereço IP
- Perguntas feitas no chat de IA (os primeiros 200 caracteres, sem a resposta), excluídas após 30 dias
- Segredos criptografados de todas as integrações de terceiros que você configurou

### O que não armazenamos

- Seu código-fonte. Clonamos o repositório no momento do build. A árvore de trabalho é descartada junto com o contêiner do build.
- Credenciais do GitHub de longa duração. Consulte **Tokens e segredos** acima.
- Senhas de usuários em qualquer formato reversível.
- Números de cartões de pagamento. A Stripe mantém todos os dados dos cartões. Armazenamos apenas o ID do cliente e os metadados da assinatura.

### Acesso interno

O acesso aos dados de produção é limitado a um pequeno número de funcionários que precisam deles para operar o serviço ou responder a solicitações de suporte. O acesso é registrado.

## Isolamento de builds

Cada build da documentação é executado em um contêiner dedicado:

- Sem acesso aos dados de outros clientes
- Ambiente novo para cada build, com segredos injetados apenas quando necessário
- O contêiner é destruído após a conclusão ou falha do build

## Conformidade

### GDPR

**A Jamdesk está em conformidade com o RGPD? Sim.** A Jamdesk atende aos requisitos do RGPD com:

- Um [Adendo de Processamento de Dados](https://jamdesk.com/dpa) que se aplica automaticamente, com uma cópia assinada por ambas as partes disponível mediante solicitação pelo endereço `privacy@jamdesk.com`
- Uma lista pública de subprocessadores em [jamdesk.com/subprocessors](https://jamdesk.com/subprocessors)
- Solicitações de exclusão atendidas em até 30 dias
- Portabilidade de dados por meio de exportação

### Privacidade

Nossa análise integrada:

- Não usa cookies. Um ID de sessão aleatório fica no armazenamento de sessão do navegador até que a aba seja fechada
- Não compartilha dados com redes de publicidade
- Não registra endereços IP dos visitantes

Consulte nossa [Política de Privacidade](https://jamdesk.com/privacy) para mais detalhes.

## Resposta a incidentes

Nossa resposta a um incidente de segurança que afete sua conta ou seus dados:

1. Investigamos e contemos o problema.
2. Notificamos os clientes afetados em até 72 horas, conforme nossas obrigações previstas no RGPD.
3. Fornecemos um relatório escrito após a confirmação da causa.

## Comunicação de vulnerabilidades

Relate problemas de segurança com responsabilidade:

- Envie um e-mail para `security@jamdesk.com`
- Inclua uma descrição, etapas para reproduzir o problema e uma avaliação do impacto
- Confirmaremos o recebimento em até 48 horas

Não temos um programa pago de recompensas por bugs. Reconhecemos pesquisadores que fazem relatos de boa-fé.
